# `.size-limit.json` policy

This document is the authoritative reference for which aihu packages carry a `.size-limit.json` row and which do not. The policy is enforced by `scripts/check-size-rows.ts`, wired as the `bun run check:size-rows` script.

## Canonical command

The canonical command for size-gate enforcement is **`bun run size`** (package-script + mangle, per Learning #47). This is the single command used by:

- CI gates (`.github/workflows/plan-a.yml`)
- PR checks
- Verifier audits during multi-agent rounds
- Local headroom decisions before dispatching plan work

The moon-orchestrator path (`moon run :size`) may still exist for bench harness invocations but is **non-canonical for size** — its output omits mangle and reads tighter or looser than the canonical depending on the package (the +15 to +83 B variance band observed in Learning #47). Do not cross-compare numbers between `bun run size` and any moon-orchestrator path output. When citing a row's headroom in a plan or commit message, the figure must come from `bun run size`.

## Why a policy exists

aihu's contract is "browser bundle ≤ 3.46 kB gz". That budget only applies to packages whose code is actually loaded into a browser bundle. Other packages — SSR-side runtimes, build-time plugins, the compiler — have legitimate footprints orders of magnitude larger and are budgeted via different mechanisms (SSR-bytes-served, dep-tree audit, install-size budgets). Mixing them into `.size-limit.json` would either pollute the browser-bundle gate with irrelevant noise or force artificial sub-kilobyte limits on code that has no business being there.

## Four classifications

Every workspace package under `packages/*` falls into exactly one bucket.

### Browser-eligible — MUST have a `.size-limit.json` row

These packages export browser-runtime code that lowers into a `dist/index.js` consumed by `@aihu/runtime` or end-user `*.aihu` SFCs. They count against the 3.46 kB ceiling.

`@aihu/primitives` is the headless-behavior package. Its budget is **per-primitive** — one `.size-limit.json` row per export entry (each its own rolldown input, so each tree-shakes independently), every primitive row under **4 KB gz** plus the shared DOM-walk context util under **1 KB gz**. There is deliberately NO single bundled `@aihu/primitives` row; the lint (`check-size-rows.ts`) treats a package as satisfied when sub-entry rows (`<pkg>/<entry>`) exist.

Adding a new browser-eligible package is the trigger for a new row. The CI lint will fail the build if a package adds `src/index.ts` and is not classified server-side or build/dev-time-only.

### Server-side — MUST NOT have a row

These packages run on a Node/Bun server and are budgeted by SSR-bytes-served plus a dep-tree audit. They never ship to a browser bundle.

- `@aihu/server` — SSR runtime (`engines.node` requirement)
- `@aihu/agent-server` — server-side MCP/bridge glue: mounts a component in a jsdom host and drives it via the agent-service gate (depends on `jsdom` + the MCP SDK; `engines.node` requirement)
- `@aihu-plugin/agent-readiness` — content-negotiation + llms.txt helpers (depends on `@aihu/server`)

If you find yourself wanting to import these from browser code, that's the bug — fix the dependency direction, do not add a row.

### Build/dev-time-only — MUST NOT have a row

These packages run in the build toolchain or dev tooling. They never reach a browser bundle.

- `@aihu/plugin` — plugin API helpers consumed by user `vite.config.*` etc.
- `@aihu/compiler` — Rust-backed `.aihu` SFC compiler with a thin JS wrapper

### Source-distributed — MUST NOT have a row

These packages ship `.aihu`/source plus a generated index, never a runtime bundle. The consumer copies the source via `aihu add` and their **own** build measures the copied output — so nothing from the package itself is bundled into a browser, and there is nothing for `.size-limit.json` to measure here. Real post-compile size accountability for the copied recipes is the fresh-project portability harness (CSS-engine Plan 6).

- `@aihu/ui` — styled-recipe registry. Source-distributed via `aihu add`; the consumer's build measures the copied recipes, not this package. It has no `dist`, no runtime entry, and deliberately no `src/index.ts` — the lint (`check-size-rows.ts`) classifies it `source-distributed` and asserts it carries no row regardless. (CSS-engine Plan 5, decision D-2.)

## Apps are NOT `.size-limit.json` rows — they self-budget in their build

`.size-limit.json` measures `packages/*` library outputs by **re-bundling each entry from source** through `scripts/size.ts` (rolldown `generate()`). `apps/docs/dist/docs.js` is an already-bundled application artifact, not a library entry — feeding it back through `size.ts` re-bundling is wrong (it double-measures and, empirically, segfaults rolldown). `check-size-rows.ts` only walks `packages/*`, so an `apps/docs` row would also surface only as a non-matching-package warning, never an enforced gate.

So the docs bundle budgets itself **in its own build**: `apps/docs/build.ts` gzip-measures `dist/docs.js` right after the client bundle and hard-fails if it exceeds the cap (currently 40 KB gz; the real bundle is ~27.5 KB gz after the WS5 `window.__DOCS__` blob removal). That assertion runs on every `bun run build` (CI builds docs before deploy), so a payload regression — e.g. re-inlining doc HTML into the client bundle — blocks the pipeline. This keeps `.size-limit.json` purely about library packages while still giving the app a real, enforced budget (WS5).

## Adding or removing a row

When adding a browser-eligible package:

1. Add the row to `.size-limit.json` with a conservative limit (round up from current `bun run size` output by ~10 %).
2. Update the table above.
3. `bun run check:size-rows` should remain green.

When promoting a server-side or build/dev-time package to browser-eligible (rare; treat as a v-bump):

1. Update the classification allowlist in `scripts/check-size-rows.ts`.
2. Add the row to `.size-limit.json`.
3. Update this README and `bench/signals/HARNESS.md` § "Size budgets".
