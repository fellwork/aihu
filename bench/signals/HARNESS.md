# `bench/signals` Harness Guide

This document tells a fresh reader how to add a workload, add a competitor, and how the CI regression gate works. **Do not modify a workload after a baseline lands** — that invalidates the regression gate. Add a new workload alongside.

## Layout

```
bench/signals/
├── package.json             # pinned competitor versions (Phase 2.5: see deps)
├── tsconfig.json            # extends repo base
├── moon.yml                 # tasks: run, size, typecheck
├── HARNESS.md               # this file
├── RESULTS.md               # latest results, regenerated by `bun run` runner
├── CHANGELOG.md             # append-only history of bench results
└── src/
    ├── runner.ts            # entry point — runs every workload × competitor, writes RESULTS.md
    ├── size.ts              # gzipped-size table (stretch deliverable)
    ├── types.ts             # SignalAdapter + WorkloadDefinition interfaces
    ├── competitors/
    │   ├── index.ts         # ordered list of adapters
    │   ├── scribe.ts        # @scribe/signals
    │   ├── alien.ts         # alien-signals
    │   ├── preact.ts        # @preact/signals-core
    │   ├── vue.ts           # @vue/reactivity
    │   ├── solid.ts         # solid-js (imports dist/solid.js, NOT main)
    │   └── sjs.ts           # s-js
    └── workloads/
        ├── index.ts         # ordered list of workloads
        ├── cellx.ts
        ├── wide-fanout-100.ts
        └── batched-writes-100.ts
```

## Running locally

```bash
cd bench/signals
bun src/runner.ts          # ~30s on a modern laptop; writes RESULTS.md
bun src/size.ts             # prints the gz size table
```

The runner takes ~1s of CPU time per (workload × competitor) cell. Three workloads × six competitors = 18 cells = ~18 s CPU + warm-up overhead. Expect 30 s wall-clock.

## Adding a workload

1. Create `src/workloads/<slug>.ts` exporting a `WorkloadDefinition`. The shape:

   ```ts
   import type { SignalAdapter, WorkloadDefinition } from '../types.ts'

   export const myWorkload: WorkloadDefinition = {
     name: '<slug>',                  // appears in RESULTS.md table headers + CI gate keys
     description: 'one-sentence',     // shown above the table
     build(adapter: SignalAdapter) {
       const ctx = adapter.setup(() => {
         // BUILD the reactive graph here. This runs once per cell, NOT per op.
         const [src, setSrc] = adapter.signal(0)
         const dispose = adapter.effect(() => { src() })
         let counter = 0
         return {
           run: () => { counter++; setSrc(counter) },  // ← what mitata times
           dispose,
         }
       })
       return {
         run: ctx.value.run,
         cleanup: () => { ctx.value.dispose(); ctx.dispose() },
       }
     },
   }
   ```

2. Register it in `src/workloads/index.ts`:

   ```ts
   import { myWorkload } from './my-workload.ts'
   export const workloads = [cellx, wideFanout100, batchedWrites100, myWorkload] as const
   ```

3. Run `bun src/runner.ts` to regenerate `RESULTS.md`. Append to `CHANGELOG.md` with the date and a note about why the workload exists.

**Sizing rule.** Each workload file should be ~50–100 lines. If it grows past 150, split the setup into a helper file in `workloads/_helpers/`.

**The single op should not allocate large objects.** mitata samples thousands of times; allocating arrays per op confounds the timing. Set up the graph once in the closure, vary only the values written.

**Use `globalThis` reads to defeat dead-code elimination.** V8 will remove computed reads whose results are never used. The pattern `(globalThis as { __sink?: number }).__sink = sum` keeps the reads live.

## Adding a competitor

1. Find the lib's stable npm version. Pin in `package.json` (no `^` or `~`).

2. Create `src/competitors/<slug>.ts` exporting a `SignalAdapter`. The shape:

   ```ts
   export const lib: SignalAdapter = {
     name: 'lib-name',          // exact npm name; appears in RESULTS.md
     version: '1.2.3',          // for CHANGELOG cross-reference
     signal<T>(init: T) { /* ...returns [get, set] */ },
     computed<T>(fn: () => T) { /* ...returns getter */ },
     effect(fn: () => void) { /* ...returns dispose */ },
     batch?: (fn: () => void) => void,           // OPTIONAL
     setup<T>(fn: () => T) { /* ...returns { value, dispose } */ },
   }
   ```

3. Register it in `src/competitors/index.ts`. **scribe stays first** in the list; otherwise order by descending market share.

4. Common gotchas:
   - **Solid resolves to a no-op server build under the `node` condition.** Import directly from `solid-js/dist/solid.js`. See `competitors/solid.ts`.
   - **Vue effects need an `EffectScope`** to be torn down between runs. See `competitors/vue.ts`.
   - **S.js requires `S.root(disposer => ...)`.** Use the adapter's `setup()` function, not the workload body.
   - **Adapters that auto-track reads inside a getter** (most of them) work without ceremony. If a lib uses explicit `subscribe(get, fn)`, restructure the adapter to call `effect(fn)` once and have `fn` close over `subscribe`.

## Performance gotchas

- **First samples are noisy.** mitata's `warmup_samples: 50` handles this; do not lower it.
- **GC pauses skew p99.** mitata reports them in `stats.gc` if `gc: true` is passed. We don't enable that in v0; if scribe's GC behavior becomes a topic, turn it on.
- **Bun and Node may disagree by 5–10%.** All numbers in `RESULTS.md` are Bun. CI uses Bun. If you run locally on Node and see different numbers, that's expected.
- **CPU thermal throttling on long runs.** The runner caps each cell at 1 s CPU. Total runtime ~30 s, well under throttle threshold on a modern laptop.

## CI regression gate

The bench runs in `.github/workflows/plan-a.yml` (job: `bench`) under these conditions:

- Triggered by changes to `packages/signals/**` or `bench/signals/**`.
- Runs `bun src/runner.ts` and writes a fresh `RESULTS.md`.
- Reads the previous `RESULTS.md` from the merge base on `main`.
- For each workload, computes `(current.p50 / previous.p50) - 1` for the `@scribe/signals` row.
- **Fails if any value exceeds `0.10` (10 % regression).**

The previous `RESULTS.md` carries a machine-readable JSON block at the bottom (between `<!-- bench-data:start -->` and `<!-- bench-data:end -->` markers). The CI script parses that block; humans read the markdown table above it.

### Override path: `[bench-bump]`

When a correctness fix legitimately slows a path (e.g. Phase 2's equals-wiring pivot added ~70 B and ~5 % perf cost), the PR commit message can include the literal token `[bench-bump]` and the gate will pass. Use sparingly; the PR description must justify.

```
fix(signals): wire equals comparator to cascade [bench-bump]

cellx p50 regresses 6 % because each notify path now allocates one extra
closure for the equality call. Acceptable cost — correctness fix per
Finding 3 (Verifier audit).
```

### When to bump the threshold

If three independent regressions in 24 hours all cluster around 8–9 %, the threshold is too tight for the noise floor. Bump to 0.15 in `.github/workflows/plan-a.yml` and document in `CHANGELOG.md`. Don't disable the gate.

### Competitor versions are not regression triggers

When a competitor publishes a faster release, scribe's relative numbers drop without scribe changing. **Bumping a competitor pin is its own commit** with `[bench-bump]` in the message. The PR description must include the before/after numbers.

## What lives where (decision tree)

| Question | Answer |
|---|---|
| Is this a runtime change? | `packages/signals/`. Bench gate fires. |
| Is this a new bench shape? | `bench/signals/src/workloads/`. No gate trigger; baseline appears next run. |
| Is this a new competitor? | `bench/signals/src/competitors/`. Pin in `package.json`. |
| Is this a measurement bug? | Fix the runner. Add `[bench-bump]` to the commit since numbers will shift. |
| Did Bun/Node major-version? | Re-baseline. `[bench-bump]`. Note the runtime in CHANGELOG. |
