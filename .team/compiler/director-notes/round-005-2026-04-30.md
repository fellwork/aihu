## 3. Risk flags for C-4

### R1 — Split between Rust binary and npm wrapper (structural risk)

C-4 introduces two distinct artifacts that live in the same `packages/compiler/` directory:

1. **Rust binary** (`aihu-compile`): a `[[bin]]` target in `Cargo.toml`. Produces a native executable via `cargo build --release`.
2. **npm package** (`@aihu/compiler`): TypeScript source in a new `packages/compiler/src/` subdirectory (or a parallel `packages/compiler/js/` tree). Exports `transform(source, id): { code, map }` and a Vite plugin.

These two artifacts require different build toolchains (cargo vs. rolldown) inside the same package directory. The existing packages use `rolldown.config.ts` for build and `moon.yml` for task registration. The `packages/compiler/` directory currently contains only Rust source. C-4 must add JS/TS source alongside it.

**Directory collision risk:** The convention in every existing package is `src/index.ts` as the rolldown entry point. If the Architect places JS source at `packages/compiler/src/`, it will co-inhabit the directory with Rust's `packages/compiler/src/lib.rs`. This is physically viable (Rust and TS are separate toolchains that ignore each other's files) but looks messy and may confuse Moon's language detection. The safer pattern is a parallel subtree: `packages/compiler/js/index.ts` as the JS entry point, with `rolldown.config.ts` pointed at `js/index.ts`. The Architect must make this call and document it in Section 17.

### R2 — npm package integration with the monorepo toolchain (moderate risk)

Every existing npm package follows the same shape: `package.json`, `moon.yml`, `rolldown.config.ts`, `tsconfig.json`, `src/index.ts`, `dist/`. Adding `@aihu/compiler` means:

- A new `package.json` at `packages/compiler/package.json` with `name: "@aihu/compiler"`. The root `bun.lock` and workspace glob (`packages/*`) already include this path once `package.json` is present — no root changes needed.
- A `moon.yml` with `language: typescript` and a `build` task pointing at rolldown. The Rust `cargo` tasks must also be registered or at minimum documented in moon.yml (as a `command: cargo build --release` task).
- A `tsconfig.json` extending `../../tsconfig.base.json`.
- Vite must be listed in `package.json` under `peerDependencies` (not `dependencies`) since it is external in the rolldown config.

The Moon workspace picks up `packages/*` automatically. The root `package.json` does not need modification. `bun.lock` will need a `bun install` run after `package.json` is added. The Builder must be reminded that `bun install` at the root is required before running any `bun` script in the new package.

The existing `agent-readiness` package is the best reference: it marks `vite` as external in `rolldown.config.ts` and uses a minimal inline `VitePlugin` interface rather than importing from `'vite'` directly. The `@aihu/compiler` Vite plugin should follow the exact same pattern.

### R3 — C4-6 (`bun vite build` integration): end-to-end build test (high complexity)

C4-6 requires a `demo/` or `test/` fixture that:

1. Contains a `.aihu` file (e.g., `counter.aihu`).

The new `packages/compiler/package.json` must include `vite` as a `devDependency` or `peerDependency`. Check whether Vite is transitively available via the root `devDependencies` before adding it — it currently is not listed there but rolldown is.

Given the local-CI-only constraint (no GHA until v1), a `bun test` integration test in `packages/compiler/tests/` is preferred. ### R4 — C4-5 Vite transform hook: the `transform` export shape

The `transform(source, id): { code, map }` interface is what Vite calls on every file matching `*.aihu`. The implementation is:

```typescript
// packages/compiler/js/index.ts
import { compile_full, emit } from './wasm-or-native.js'

export function transform(source: string, id: string): { code: string; map: null } {
  const stem = path.basename(id, '.aihu')
  const unit = compile_full(source)
  const code = emit(unit, stem)
  return { code, map: null }
}
```

The key unresolved question is **how the TypeScript wrapper calls the Rust compiler**. There are two options:

- **Option A — subprocess**: The TS `transform()` function spawns `aihu-compile --stdin` and reads stdout. Simple, no WASM build chain needed, but requires the Rust binary to be on PATH or at a known relative path.
- **Option B — WASM**: Compile `aihu-compiler` to `wasm32-wasi` or `wasm32-unknown-unknown`, bundle it into the npm package. No external binary dependency, but adds a WASM build step, `wasm-bindgen` dependency, and increased `packages/compiler/Cargo.toml` complexity. This is out of scope for v0.

**Director decision: use Option A (subprocess) for v0.** The binary is co-located in the repo; the Vite plugin can resolve its path relative to `import.meta.url`. The Architect must document exactly how the TS plugin locates the binary (e.g., via a `SCRIBE_COMPILE_BIN` env var with a fallback to `../target/release/aihu-compile`). This is a known fragility — document it as a v0 limitation.

## 4. Scope decision on C4-7 (source maps)

**C4-7 is deferred. It must not be a hard acceptance criterion for C-4.**

Rationale:

1. **The Rust emit pipeline has no line-tracking infrastructure.** `emit()` produces a `String` assembled from format strings without recording source positions. Retrofitting source map generation would require threading a `source_pos: usize` through every `emit_node()` and `emit_attrs()` call, then encoding VLQ base64 mappings per the Source Map v3 spec. This is a significant algorithmic addition — materially larger than all of C-4's other work combined.

2. **The `transform()` return type already accommodates deferral.** Returning `{ code, map: null }` is valid in Vite. The TypeScript type for Vite's transform hook accepts `map: null | RollupSourceMap`. A null map means Vite falls back to no source-map-based debugging, which is the correct v0 behavior.

3. **OQ-C8 was already formally deferred to C-4 from C-0.** The prior director notes record "Deferred to Phase C-4" as the resolution, but the original OQ acknowledged the complexity. This note converts that soft deferral into a hard v1 scheduling decision.

**C4-7 replacement criterion:** Replace C4-7 with a null-map stub criterion: "The `transform()` return value's `map` field is `null` in v0. A comment in `packages/compiler/js/index.ts` documents 'source maps deferred to v1, tracked as OQ-C8'." The Verifier must check that no `map` data is emitted (to avoid accidentally shipping a corrupt map).

This frees the Architect and Builder to focus on C4-1 through C4-6, which are already high in surface area.

## 6. Builder brief — highest-risk implementation areas

**B1 — Do not touch `packages/compiler/src/lib.rs` beyond adding the binary path.** The `lib.rs` public API is stable; the CLI binary calls `aihu_compiler::compile_full()` and `aihu_compiler::emit()` as a library consumer. Any change to `lib.rs` function signatures will break 32 existing snapshot tests. The binary lives in `src/bin/main.rs` and imports from `super::` or `aihu_compiler::`.

**B2 — HashMap ordering in `SignalMap` is non-deterministic.** This is the known risk from C-3. The `emit()` function calls `resolve_signals()` internally, which returns a `HashMap`. In C-4, `emit()` is called from the CLI binary and from the Vite transform. The existing 32 tests already accommodate this (snapshots were re-accepted). New C-4 tests must also tolerate it: any test that exercises `emit()` with multiple signals must use `INSTA_UPDATE=always` on first run and accept that snapshot ordering is environment-dependent. Do not add new `SignalMap` snapshot tests that assert ordering. If a C-4 test needs to check multi-signal output, use a `contains()` assertion rather than a full snapshot.

**B3 — Subprocess error propagation in the Vite transform.** When `aihu-compile` exits non-zero, the Vite plugin must surface the error cleanly — not crash the Vite dev server. The TypeScript wrapper must catch the non-zero exit, extract stderr, and throw a `new Error(stderr)`. Vite will then display it as a build error. A swallowed exception here would produce a silent empty `dist/` file.

**B4 — Binary not on PATH in CI context.** The integration test for C4-6 needs the compiled binary. The Builder must ensure the integration test either builds the binary first (`cargo build --release`) or documents that the binary must be pre-built before the integration test runs. Do not assume the binary is already on PATH.

**B5 — `rolldown.config.ts` external list.** The new `@aihu/compiler` rolldown config must mark `vite` as external (same as `agent-readiness`). If `node:child_process` or `node:path` are used, they must also be external. Failing to mark them external will cause rolldown to attempt to bundle them and error out.

**B6 — `bun install` required before first `bun run build` in the new package.** When `package.json` is first added to `packages/compiler/`, running `bun install` at the repo root is required to create the workspace symlink. The Verifier will need to do this before any TS build steps in the new package.
