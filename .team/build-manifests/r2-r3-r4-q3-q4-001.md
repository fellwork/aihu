### R4 — `$bind.value` two-way write-side

**Spec source:** Director r6 §3.R4; platform-audit §3.

**Verifier-flagged ambiguity:** the Verifier had flagged that read-side wiring works (lower_attr_expr emits `[get, set]` signal tuple), but write-side might or might not be wired. **Builder finding:** write-side was MISSING. `_applyAttrs` Path 2 (`Array.isArray(value)`) only reads `value[0]` — the setter `value[1]` never gets attached to user-input events. Implementation choice: detect `$bind:` macros at compile time and emit a paired `oninput` (or `onchange` for `checked`) event handler in the same attrs object that calls `setter(e.target.value)` (or `e.target.checked`).

**Files changed:**

Auto write-back is suppressed when the user already wrote `$on:input`/`$on:change` (intent wins). ~50 LOC.

## Decisions (Builder picks)

1. **R2 dispatch order**: R1's $prop signal-update runs FIRST (existing `attributeChangedCallback` path); userland `attributeChange` runs SECOND inside the same callback. Matches Director r6 §3.R2 explicit guidance ("authors see the post-converted signal value").

2. **R3 emit shape**: `el.toggleAttribute('hidden', !(cond))` rather than `el.setAttribute('hidden', '')` / `el.removeAttribute('hidden')` pair. WHATWG spec'd primitive for "set if true, unset if false"; one DOM call per signal update vs branching, slightly tighter emit.

3. **R4 event choice**: `oninput` for `value`-bound props; `onchange` for `checked`-bound (WHATWG checkbox/radio convention). All other `$bind:propname` defaults to `onchange` (custom elements typically dispatch CustomEvents that override anyway).

4. **R4 write-back suppression**: when userland already wrote `$on:input` (or `$on:change`), the auto write-back is silently suppressed. Userland intent wins; authors who want both compose them explicitly. This is the conservative choice — alternative was wrap user handler with our write-back, but that breaks reasoning about "what does this handler do."

5. **Q3 guard mechanic**: `_isInternalAttrChange` boolean flag on the host, NOT a Set. Director r6 §2.Q3 default (Lit's `_isReflecting` precedent). Simpler than per-attribute granularity; one host can only be inside one attributeChangedCallback at a time per the platform contract (synchronous; not reentrant across attributes).

6. **Q4 location**: collision detection lives in `parse_state_macros` after multiplicity-check but before `Ok(result)`. A compile-time error here surfaces in compile_full's normal error path (snapshot + path + code chain). Alternative was post-parse semantic-pass over StateMacro nodes — same effect, deferred for no benefit.

## Open questions / surfaces

None block. Two notes for r7 governance:

1. **R4 write-back: typed conversion?** The auto-write-back currently calls `setName(e.target.value)` which is always a `string`. If userland declared the signal as `signal(0)` (number), the write-back stores `'5'` not `5`. Director may want a typed-conversion at the bind site (mirror R1's `_convert` direction). Surfacing — not implemented in B2 per literal AC.

2. **Q3 guard scope**: `_isInternalAttrChange` is host-wide (one flag). If two attributes change simultaneously (synchronous burst, e.g. `el.setAttribute('a', 'x'); el.setAttribute('b', 'y')`), the guard correctly straddles both because they fire sequentially. If a future feature batches attribute writes asynchronously, this assumption needs re-verification.
